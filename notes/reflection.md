# Reflection: fine-tuning vs RAG for an ATT&CK specialist

**Setup.** I fine-tuned Llama-3.2-3B-Instruct (QLoRA, rank 32, 2 epochs, 348 steps, about 14.5 minutes using Unsloth Studio) on 1,385 chat conversations built from the 609 MITRE ATT&CK techniques created up to 2023-12-31. The 88 techniques created after that date were held out on purpose. I exported the model as a Q8_0 GGUF and ran it in Ollama as `attack-analyst`. The RAG pipeline (`attack_rag.py`) uses ChromaDB with the `nomic-embed-text` embedding model. It holds 757 chunks: 697 ATT&CK technique documents plus 60 sections of the OWASP LLM Top 10 (2025), which the model never saw in training. Retrieval combines exact-ID lookup with semantic search, and a plain-code grounding check tests whether the cited files and IDs really appear in the retrieved documents.

## What fine-tuning added over the base model
Fine-tuning changed **how** the model answers. The base Llama rambled for paragraphs or hedged ("I don't have information..."). The fine-tuned model answers in the same structured brief every time: technique ID, tactic, platforms, summary, mitigations, detection. It also learned the habit of citing a source file when documents are provided.

It did **not** add reliable facts. For Q1 (a process dumping lsass.exe memory with comsvcs.dll) the correct answer is T1003.001, LSASS Memory. The fine-tuned model, without retrieval, answered "T1134.002 Memory Dumping (sub-technique of T1134 Memory Injection)" in a perfect-looking brief, but T1134 is really Access Token Manipulation and T1134.002 is Create Process with Token, so that technique name is made up. For Q2 (Volt Typhoon clearing Windows Event Logs, a technique created in April 2026 and held out of training), it invented "T1070.003 Clear System Logs" (T1070.003 is really Clear Command History). A confident, well-formatted wrong answer is arguably more dangerous than the base model's rambling. The base model was also wrong: it hedged and offered invented names such as "T1210: Use of Windows Management Instrumentation (WMI)" (T1210 is actually Exploitation of Remote Services) and, for Q2, "T1003: Clearing logs" (T1003 is OS Credential Dumping). Outputs vary a little from run to run even at low temperature, so the exact wording in my screenshots is one run, not a fixed result.

Fine-tuning also made the model over-specialized. Asked about OWASP LLM08:2025, it printed an ATT&CK technique brief with made-up content, even when the correct OWASP text had been retrieved. I worked around this in the RAG layer by using a plain-prose prompt when the retrieved documents are OWASP files. The proper fix would be more varied training data.

## What RAG added over the fine-tuned model alone
RAG supplied the facts at question time. With retrieval, Q1 returned T1003.001 LSASS Memory and Q2 returned T1685.005 Clear Windows Event Logs. Both answers matched the source records, including parent technique, tactic, mitigations and detection, and both cited the source file (`T1003.001.txt`, `T1685.005.txt`). Q3 returned the correct OWASP name (Vector and Embedding Weaknesses) and two mitigations taken from `LLM08_VectorAndEmbeddingWeaknesses.md`. None of this needed retraining, and the grounding check passed on all three after the fix. When the earlier Q3 attempt produced an answer with no source, the same check printed a warning, so the check is useful as a guard, not just a demo.

## When I would use each
- **Fine-tune** when the model needs a stable behavior: a fixed output format, a tone, a task skill, or the ability to read provided documents and cite them. It also helps a small, cheap model punch above its size.
- **Use RAG** when the facts change (ATT&CK changes every release), are large, or are private, and when answers must be traceable to a source. Updating means re-indexing documents, not retraining.
- **Combine them** for a system like this one: the fine-tune provides the format and the "answer only from the documents" habit, and retrieval provides the facts. Either way the answer should be verified against the cited source, because a small model can still ignore the documents.

## Limits of this evidence
This is a three-question demonstration at low temperature (0.1) on a 3B model, not a benchmark. Retrieval is not perfect, so a missed document would produce a wrong or abstained answer. The fine-tuning run was short (2 epochs), and a longer or more varied run might memorize more facts, but RAG would still be the better home for facts that change.
